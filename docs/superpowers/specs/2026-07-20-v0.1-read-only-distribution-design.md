# v0.1 Read-only Distribution Design

**Status:** auto-approved product design

## Outcome

Ship the existing Product 1 read-only slice as an installable `0.1.0` release candidate. A user configures
one private OPNsense connection file, then launches the same npm package from Codex, Claude Code, OpenCode,
or Kimi Code. Client configuration never contains the API key or secret.

## Scope

The v0.1 surface remains exactly `server_status`, `opn_describe`, `opn_get`, and `opn_list`, backed by
`system.status` and `core.services`. It does not add a mutation, backup claim, dashboard, arbitrary API
dispatcher, shell access, broad resource catalogue, benchmark score, or Internet-exposure workflow.

## Considered approaches

1. Documentation snippets only: quickest, but still makes every user design secret storage and command
   paths. Rejected as the primary experience.
2. One npm package, a secure configuration command, deterministic default paths, and native client adapters:
   selected. It minimizes release artifacts and keeps every client on the same tested executable.
3. One independently published package per client: rejected for v0.1 because it multiplies versioning,
   provenance, and platform gates without adding OPNsense capability.

## Product contract

- `npx -y @gabrielion/opnsense-mcp@0.1.0 configure` collects credentials interactively and writes one
  private JSON file. Credentials are never accepted in argv and never printed.
- With no explicit `OPNSENSE_CONFIG_FILE`, the server discovers that platform's deterministic default file.
  An explicit environment override remains available for labs and advanced setups.
- POSIX configuration is owned by the current user, mode `0600`, link count one, regular, and non-symlink.
  The containing application directory is private. Native Windows support must apply and verify an equivalent
  protected ACL before it is claimed.
- The server command remains protocol-clean stdio. Configuration and diagnostics are explicit CLI
  subcommands and never run during MCP startup.
- The npm tarball contains precompiled JavaScript and has no lifecycle installation step or native helper.
- Codex and Claude receive native plugin/marketplace metadata plus direct MCP fallbacks. OpenCode receives its
  documented local MCP configuration. Kimi uses the current `kimi-code` MCP format, not obsolete `kimi-cli`
  instructions.
- Support claims are evidence-specific: a documented recipe is not called tested until a versioned smoke
  succeeds. Windows is the final native pre-publication gate.

## Release boundary

The npm package is the release artifact. MCP Registry metadata is prepared but publication waits until the
exact public npm tarball is available because the Registry is discovery metadata, not package hosting.
`private: true` is removed only with tests that inspect the packed artifact and publication metadata.

## Proof

The deterministic gate packs the package, installs it with scripts disabled, exercises MCP initialize/list,
checks the configuration path and secret-file rules, validates plugin/config manifests, and confirms the
tarball contains no credentials or development-only files. Existing synthetic HTTPS, disposable-VM,
conformance, OpenCode, license, provenance, and full-suite proofs remain required. Native Windows must repeat
pack/install, `.cmd` launch from a path containing spaces, ACL enforcement, MCP exchange, mock connectivity,
exact-process exit, and cleanup.
